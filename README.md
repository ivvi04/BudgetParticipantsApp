# Budget Participants

Консольное Java-приложение (Java 8, Maven): скачивает реестр УБП/НУБП из ЕПБС
(https://budget.gov.ru/epbs/registry/ubpandnubp/data) за период
`lastUpdateFrom..lastUpdateTo`, раскладывает записи в денормализованную таблицу
PostgreSQL, при необходимости переносит её в ClickHouse и архивирует ранее
скачанные ответы (JSON → XML в zip).

## Структура

    src/main/java/ru/lakeevda/budgetparticipantsapp/
      BudgetParticipantsApp.java      точка входа, оркестрация конвейера
      client/ApiClient.java           пагинация и скачивание страниц API
      config/ConfigLoader.java        загрузка application.properties из classpath
      db/                             DatabaseConnection, PostgresConnection,
                                      ClickHouseConnection
      mapper/JsonFlattener.java       JSON → плоская карта колонок
      mapper/JsonToXmlConverter.java  JSON → XML для архива
      service/DataLoadService.java    запись в PostgreSQL, динамические колонки
      service/ClickHouseTransferService.java  перенос PG → ClickHouse
      service/ZipService.java         архивация JSON в zip (XML внутри)
    src/main/resources/application.properties
    src/test/java/...                 JUnit 4 тесты

## Требования

- JDK 8;
- Docker и Docker Compose — для локальных PostgreSQL и ClickHouse (если базы уже
  доступны, не нужны);
- Maven устанавливать не обязательно: в репозитории есть wrapper — `mvnw`
  (Linux/macOS) и `mvnw.cmd` (Windows).

## Развёртывание БД

    docker compose up -d

Поднимаются:

- PostgreSQL 13 (внутри контейнера 5432, наружу проброшен **5433**) —
  образ собирается с блоками 32 КБ;
- ClickHouse 22.3 (наружу 8123 для JDBC/HTTP и 9000 для native-клиентов).

## Конфигурация

Все параметры — в `src/main/resources/application.properties` (читаются из
classpath, файл вне jar не поддерживается):

| Ключ | Назначение |
|------|------------|
| `api.url` | шаблон URL; `%1$s` = from, `%2$s` = to, `%3$s` = pageNum |
| `api.dateFormat` | формат дат в URL (`dd.MM.yyyy`) |
| `api.itemsKey` | поле с массивом записей (`data`) |
| `api.totalPagesKey` | поле с числом страниц (`pageCount`) |
| `db.table` | имя таблицы для обоих баз |
| `postgres.url` / `username` / `password` | подключение к PostgreSQL (порт 5433) |
| `storage.rawDir` | каталог для скачанных JSON и zip (`data/raw`) |
| `clickhouse.enabled` | включён ли перенос в ClickHouse |
| `clickhouse.url` / `username` / `password` | подключение к ClickHouse |

## Сборка и запуск

    # Linux/macOS
    ./mvnw clean package

    # Windows
    mvnw.cmd clean package

    java "-Dfile.encoding=UTF-8" -jar target/budget-participants-0.0.1-SNAPSHOT-jar-with-dependencies.jar 2024-01-01 2024-01-31

Имя исполняемого jar определяется `groupId`, `artifactId` и `version` из
`pom.xml`; актуальный файл всегда лежит в `target/` с суффиксом
`-jar-with-dependencies`. Если Maven установлен глобально, вместо wrapper можно
использовать `mvn`.

Обязательные аргументы: `lastUpdateFrom` и `lastUpdateTo` в формате ISO
(`yyyy-MM-dd`), иначе приложение завершается с ошибкой. Если `from > to`,
запуск прерывается. В URL сервиса даты подставляются в формате `dd.MM.yyyy`
согласно `api.dateFormat`.

## Конвейер

Порядок шагов в `BudgetParticipantsApp.run`:

1. **Архивация прошлых запусков** — все `*.json` из `storage.rawDir`
   группируются по периоду из своего имени (`page_<from>_<to>_<NNNNN>.json`)
   и конвертируются в XML внутри `archive_<from>_<to>.zip`. Архив пересобирается
   во временном файле и атомарно подменяет прежний: уже заархивированные записи
   сохраняются, совпадающие по имени — заменяются новой версией, дубликатов не
   возникает. Исходные JSON удаляются только после успешной подмены архива.
   Некорректный JSON не удаляется и в архив не попадает. Файлы, имя которых не
   соответствует шаблону, складываются в `archive_other.zip` с предупреждением
   в лог и не приписываются к чужому периоду.
2. **Скачивание** — пагинация `pageSize=500` (зашито в шаблон URL), `pageNum`
   с 1. Остановка по достижении `pageCount` или (если счётчик неизвестен) по
   пустому массиву `data`. Сырые ответы пишутся в
   `page_<from>_<to>_<NNNNN>.json`, где номер страницы дополнен нулями до
   5 цифр.
3. **Загрузка в PostgreSQL** — таблица создаётся при отсутствии. Колонки
   добавляются по мере появления новых полей (`ALTER TABLE ADD COLUMN ... text`).
   Повторная загрузка за тот же период перезаписывает данные: перед вставкой
   выполняется `DELETE ... WHERE last_update_from=? AND last_update_to=?`.
   Если запись с таким же `id` уже есть в базе (например, загружена
   за другой период), `INSERT ... ON CONFLICT (id) DO UPDATE` обновляет её
   значениями из новой выгрузки вместо ошибки нарушения первичного ключа.
   Обновляются только колонки, непустые в новой записи; поля, отсутствующие
   в выгрузке, сохраняют прежние значения. Страницы обрабатываются по одной,
   поэтому в памяти одновременно находится только одна страница выгрузки.
   Каждая страница фиксируется отдельной транзакцией: объём WAL и длительность
   блокировок не растут с размером периода. Если загрузка прервётся, период
   останется загруженным частично, но следующий запуск удалит его и загрузит
   заново.
4. **Перенос в ClickHouse** — если `clickhouse.enabled=true`: данные копируются
   в промежуточную таблицу `<table>_staging` (все колонки типа `String`,
   `ENGINE = MergeTree ORDER BY id`), после чего она атомарно подменяет основную
   через `EXCHANGE TABLES` (на серверах без его поддержки — переименованием через
   `<table>_backup`). Поэтому схема всегда соответствует PostgreSQL, повторный
   перенос не накапливает дубликаты, а при сбое прежние данные ClickHouse
   остаются нетронутыми. Строки копируются батчами по 5000 (чтение из PG —
   курсор с fetch size 1000).
5. **Логирование итога**.

## Денормализация

- Вложенные объекты разворачиваются через `_`: `info.fullName` → `info_fullname`.
- Массивы не хранятся как json/jsonb: элементы получают индекс в имени колонки —
  `heads_0_fio`, `facialaccounts_1_num`, `activities_0_activitycode`.
- Индекс элемента определяется каноническим представлением (JSON с
  отсортированными ключами и элементами вложенных массивов), а не порядком в
  ответе API, поэтому перестановка элементов в источнике не перемешивает
  значения колонок. При изменении содержимого элемента его индекс может
  измениться — индексы пересчитываются при каждой загрузке.
- `null`, пустые объекты и пустые массивы пропускаются.
- Имена колонок приводятся к нижнему регистру; недопустимые символы заменяются
  на `_`.
- В каждой записи дополнительно проставляются `last_update_from` и
  `last_update_to`.
- Вставка группирует строки по набору непустых колонок, чтобы не передавать
  NULL-параметры; размер батча = `32000 / число колонок группы`.

## Лимит колонок PostgreSQL

PostgreSQL допускает до 1600 колонок. При приближении к 1500 приложение пишет
WARN, после 1595 новые колонки не добавляются. Таблица создаётся с первичным
ключом `id text`.

Если хотя бы одно непустое значение записи ссылается на колонку, которой нет
в таблице, такая запись **не вставляется вовсе**, а по ней сразу пишется
отдельное предупреждение:

    WARNING: Запись с id 3269685 пропущена по причине превышения количества
    колонок: требуется 2023 из возможных 1595 (не поместилось 428).

В сообщении: `id` записи (или `<без id>`, если его нет), сколько всего колонок
требуется записи (`число колонок таблицы + не поместившиеся значения`) и
жёсткий лимит PostgreSQL. Сообщения не накапливаются: предупреждение выводится
по каждой пропущенной записи сразу при обработке страницы, без сводки в конце.

Записи, у которых все значения помещаются в существующие колонки, вставляются
как обычно. Каждая страница по-прежнему фиксируется отдельной транзакцией.

Повторная загрузка периода ситуацию не исправит: колонок физически нет
в таблице. Радикальное решение — вынести массивы в дочерние таблицы или
одну JSON-колонку на массив.

## Тесты

    ./mvnw test        # Windows: mvnw.cmd test

Покрыты: `ApiClient` (извлечение массива, число страниц, остановка пагинации,
имя файла и URL страницы, сохранение страницы), `JsonFlattener` (разворачивание,
санитизация, детерминированный порядок элементов массивов, вложенные массивы,
пустые контейнеры), `JsonToXmlConverter` (XML-представление), `DataLoadService`
(чтение страниц без БД, сборка INSERT/ON CONFLICT, отбор непустых колонок,
отбрасывание записей, которым не хватает колонок, и предупреждение по каждой
такой записи), `ClickHouseTransferService`
(сборка DDL и SQL, экранирование), `ConfigLoader` (чтение и значение
по умолчанию), `BudgetParticipantsApp` (валидация периода), `ZipService`
(архивация/удаление/невалидный JSON, имя архива по периоду из имени файла,
`archive_other.zip` для имён вне шаблона, повторная архивация без потери
записей и без дубликатов, сохранение исходника при ошибке записи архива).
